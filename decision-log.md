## Purpose

This log captures every non-trivial implementation decision made while executing **Config F** of the blitzy-odoo multi-tool security comparison, per AAP §0.7.1 (Explainability rule). It is the **single source of truth for "why" decisions** — code comments may exist for "how" but never for "why". The audience is the engineer onboarding to reproduce or extend the configuration.

A decision is "non-trivial" if a competent engineer could reasonably have chosen differently. Each row of the Master Decision Table records what was decided, what alternatives existed, why this choice was made, and what risks it carries. Mechanical choices (variable naming, function decomposition) and uncontroversial idioms are not enumerated unless the user directive explicitly references them.

## Scope of This Log

- **What is captured:** Install-source choice, scan-command construction, normalizer transformation rules (severity priority, CWE/CVE fallback, description selection, truncation method, path relativization), output-shape commitments (encoding, minification, line terminator, severity casing, `line: 0` literal), and theme/asset choices for the executive presentation.
- **What is NOT captured (and why):** Uncontroversial idioms with no reasonable alternative — variable naming, function decomposition, choice of stdlib `json` over rolling a parser (no reasonable alternative on Python 3), text-mode UTF-8 open (canonical on Linux Python 3).
- **Bidirectional traceability matrix:** intentionally absent. AAP §0.7.1 requires it for migrations or refactors; Config F is neither — it is an additive evidence-generation configuration that introduces only new artifacts at the working-directory root and modifies zero existing files.
- **Cross-configuration aggregation:** out of scope. Configurations A, B, C, D, E, G of the multi-tool comparison are owned by peer Blitzy runs; this log documents Config F decisions only. The aggregator's contract (the 5-key `findings-config-f.json` schema) is *defended* here but its implementation is owned elsewhere.
- **Remediation:** out of scope. The configuration's job is to **observe**, not to **act**. No package upgrades, pin changes, or vulnerability fixes are attempted.
- **CI wiring:** out of scope. `.github/workflows/` is intentionally not created in this configuration.

## Deviations from the Literal Prompt

Every divergence below is justified in the Master Decision Table; the bullets are a recap and cross-reference for the engineer auditing the run.

- **Four files written instead of "1 new file"** — `findings-config-f.json`, `results-osv.json`, `decision-log.md`, `executive-presentation.html` (Row 16). The three extra files are mandated by User Directive 2 pass/fail (`results-osv.json`), the Explainability rule (`decision-log.md`), and the Executive Presentation rule (`executive-presentation.html`).
- **Scan command uses `osv-scanner scan source --recursive` rather than the user's verbatim `osv-scanner --format json --output results-osv.json /path/to/blitzy-odoo`** (Row 3). The v2-canonical recursive form is required for OSV-Scanner v2 to reach both lockfiles; the verbatim form would silently skip `addons/iot_box_image/configuration/requirements.txt`.
- **One trailing LF appended to `findings-config-f.json`** (Rows 12 and 13). Strict no-newline emission would yield `wc -l == 0`, failing the user's literal pass/fail criterion (`cat findings-config-f.json | wc -l` returns `1`).
- **Theme CSS inlined into `executive-presentation.html`** (Row 17). The canonical theme path `blitzy-deck/references/blitzy-reveal-theme.css` does not exist in this repository; inlining honours the "single self-contained HTML" rule.
- **Prebuilt binary install path** (Row 1). The user's prompt lists `go install` and `apt install` as alternatives; the prebuilt binary is selected because Go 1.26.2+ is not present and the `apt` package is not available on Ubuntu 25.10.
- **`cvss` Python library used by the normalizer** (Row 6). The AAP §0.4.1 lists "stdlib (Python) `json`" only; the `cvss` library is added at runtime (not committed) to compute v3/v4 base scores correctly — a hand-rolled v4 macro-vector lookup table in stdlib would be high-risk.
- **Empty-severity vulnerabilities default to `low`** (Row 8). The user enum (`critical | high | medium | low`) does not include `unknown`; the AAP §0.1.3 documents `low` as the conservative-floor default rather than dropping the finding.
- **Final-fallback for `cwe` field is the OSV `vuln.id`** (Row 9). The user instruction names CWE and CVE only; the AAP §0.1.3 extends the chain to the primary `id` (e.g. `GHSA-…`, `PYSEC-…`) for the ~3 % of records that have neither CWE nor CVE.
- **Deprecated `--output` flag retained** (Row 4). OSV-Scanner v2 prefers `--output-file`, but the user's verbatim directive uses `--output`; retaining the flag minimises divergence from the prompt.
- **Whitespace preserved verbatim in description** (Row 10). Initial implementation applied `.strip()` defensively; this was reverted under Code Review Checkpoint 1 Finding #2 to honour the literal `s[:200]` rule and preserve upstream OSV bytes exactly.
