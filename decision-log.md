# blitzy-odoo Security Audit — Config A · Decision Log

This document is the Explainability-rule companion to `findings-config-a.json` and `executive-summary.html`. It records every **non-trivial** decision made during the Config A native-only security audit of the `blitzy-odoo` codebase — CWE-choice rationale, severity tie-breaks, deliberate exclusions of candidate findings, and any interpretation that deviates from a literal reading of the user directives. Trivial mechanical decisions (a routine application of the severity rubric, restatement of existing project facts) are NOT logged.

Per AAP §0.8.1.1 the rule is binding: *"Do not embed rationale in code comments. The decision log is the single source of truth for 'why' decisions."* The `description` field in `findings-config-a.json` is therefore finding-summary-only; all "why" prose lives here.

**Bidirectional traceability matrix declared NOT APPLICABLE.** The migration / refactor traceability-matrix clause of the Explainability rule does not apply to this work because the audit performs zero source-code transformation — no source construct is mapped to a target implementation. Config A is a strict read-only audit per AAP §0.4.2; the only files created are the three artifacts at the repository root (`findings-config-a.json`, `decision-log.md`, `executive-summary.html`).

**Governing AAP references.** The decisions logged below are grounded in the AAP's authoritative sections: §0.3.2 (existing controls — false-positive avoidance), §0.4.2 (out-of-scope items), §0.6.4 (severity rubric and CWE selection rule), §0.6.7 (edge cases), §0.9.1 (no external tooling, no CVE-feed lookup), §0.9.3 (honest under-reporting beats noisy over-reporting). All `<file>:<line>` anchors below correspond to entries in `findings-config-a.json` and can be joined against that dataset on `(file, line, cwe)`.

**Audit summary numbers.** 34 findings reported. Severity distribution: 9 high, 16 medium, 9 low, 0 critical (the rationale for zero critical findings is recorded in §5). The single largest CWE class is **CWE-1104** (15 findings, 44%) from `requirements.txt` outdated pins; the most consequential cluster is **CWE-798** (7 findings, 21%) covering the `admin` default master-password chain.

## §1. Audit scope decisions

| Decision | Alternatives Considered | Why This Choice | Risks |
| --- | --- | --- | --- |
| **Scope = read-only audit, zero source changes.** | (a) Propose patches inline next to each finding; (b) attach unified-diff files in a separate folder. | AAP §0.4.2 forbids modifying any existing repository file. Config A is the baseline against which Configs B/C/D will be measured, and any source change would invalidate the comparison. | A reviewer who interprets "audit" to include remediation will expect patches and find none; the closing-slide and the `SECURITY.md` reference define the actual disclosure pathway. |

| **Documentation excluded** (`doc/**`, `docs/**`, `.github/**`, `.weblate.json`, `mkdocs.yml`, translation files). | Audit all markdown / HTML for embedded JavaScript or unsafe template constructs. | Documentation is not executable surface; AAP §0.4.2 lists it as out of scope. | A documentation-rendering pipeline that ingests untrusted user input (none observed in this repo) could carry XSS that this audit misses. |
| **Dependency files inspected but not modified** (`requirements.txt`, `setup.py`, `setup.cfg`, `ruff.toml`). | Update pins in `requirements.txt` to remediate the 15 CWE-1104 findings inline. | AAP §0.4.2 forbids remediation; outdated components are reported as CWE-1104 findings anchored at their declaration line and left for the disclosure pipeline to action. | A reader expecting actionable version bumps will find none in this baseline — the executive deck and `SECURITY.md` triage path mitigate this. |
| **Bundled Nginx config IS in scope** (`setup/win32/conf/nginx/nginx.conf`). | Treat the file as advisory / sample only and exclude. | The file ships in the repository; AAP §0.3.1 anchors it as the canonical example finding (TLSv1/TLSv1.1) and AAP §6.4.3.6 carries the explicit production-security warning for the same artifact. | Some deployments override this config entirely — the finding tags the bundled reference, not every deployment in the wild. |

| **No CVE-feed lookup performed.** | Cross-reference each `requirements.txt` pin against an OSV / NVD / GitHub Advisory feed and cite specific CVE IDs from current data. | AAP §0.9.1 forbids web-search-derived CVE feeds for Config A; the CWE-1104 findings rely on the agent's internalized knowledge of which pin versions are publicly known-vulnerable. | A few CVE numbers cited in finding `description`s are recalled from training data — they are accurate at recall time but not freshly fetched and may have superseding advisories. |
| **Deterministic ordering of findings: `(file lexicographic, line ascending)`.** | Severity-descending grouping; CWE-grouped clustering; chronological / discovery order. | AAP §0.6.4 mandates stable ordering so Configs B/C/D can join findings on `(file, line, cwe)` keys for delta analysis. | Severity-grouped reading is slightly less natural for human reviewers — the executive deck compensates with KPI cards and CWE-family breakdowns. |

| **`addons/iot_drivers/tools/upgrade.py:204` → CWE-78 at `medium`.** | CWE-77 (Improper Neutralization of Special Elements used in a Command — generic). | CWE-78 is the deeper child of CWE-77 and is specifically scoped to OS / shell commands; the sink is `subprocess.run(..., shell=True)`. | A reader mapping against CWE-77 will not pick this up via CWE filter; description names `subprocess.run(..., shell=True)` explicitly. |

CWE-95 is not the right fit because there is no `eval`-class evaluation in this sink. | If the URL only ever holds a pre-URL-encoded `route`, the finding is academic; the YouTube branch derives a less-sanitized `token` and motivates keeping the finding. |

## §3. Severity tie-break decisions

| Decision | Alternatives Considered | Why This Choice | Risks |
| --- | --- | --- | --- |
| **`addons/web/controllers/database.py:73,96,113,129,152` auto-password-reset cluster → `high` (not `critical`).** | `critical` (treated as remote unauthenticated authentication-bypass on a public route). | The five routes are gated by *both* `auth='none'` AND the runtime condition `verify_admin_password('admin') == True`. If the operator changes `admin_passwd` to any value before exposing port 8069, the condition collapses — so exploitability is precondition-dependent, which the rubric (AAP §0.6.4) places at `high`, not `critical`. | An operator who installs Odoo, exposes the DB-manager UI to the internet, and never rotates the master password is one HTTP request away from full control; a reader who scores by worst-case outcome would defensibly say `critical`. |
| **`setup/win32/conf/nginx/nginx.conf:12` → `high` (not `critical`).** | `critical` (broken cryptography in a production path with no preconditions). | This is the *bundled reference* config — many operators override it with their own Nginx config or terminate TLS at a different layer. The rubric §0.6.4 places "broken cryptography in a production path" at `high`, reserving `critical` for unauthenticated RCE-class issues. | If operators deploy unchanged, downgrade attacks against TLSv1 / TLSv1.1 are real; a reader who scores by worst-case impact would defensibly say `critical`. |
| **`requirements.txt:47` Pillow 9.0.1 → `high`.** | `medium` (impact dampened by the authentication requirement on most upload paths). | Pillow 9.0.1 carries multiple image-parser CVEs in the CVE-2022-22815 / 22816 / 22817 / CVE-2022-30595 / CVE-2023-44271 family; image parsing is reachable from authenticated upload features that are present across many addons (mail attachments, attachment widgets, image fields, OCR pipelines). | `medium` is defensible if one argues the upload paths require authentication; `high` chosen here because Pillow is broadly reachable and the CVE set spans crash-to-RCE-class issues. |
| **`requirements.txt:89` Werkzeug 2.0.2 → `high`.** | `medium` (impact dampened by typical reverse-proxy hardening). | Werkzeug 2.0.2 is the WSGI layer for every HTTP request; the CVE-2024-34069 (debugger PIN bypass) and CVE-2023-46136 (multipart DoS) class are reachable for any operator who exposes Odoo and the dependency is universal across all deployments. | If an operator runs behind a reverse proxy that strips debug routes and limits multipart payload sizes, the impact is reduced; severity stays at `high` because the dependency is universally loaded. |
| **`requirements.txt:12` cryptography 3.4.8 → `high`.** | `medium` (impact limited to specific code paths that parse exotic cert extensions). | CVE-2023-0286 (X.400 type confusion in `cryptography`'s X.509 parsing) is high-severity and the library underpins TLS / cert / JWT parsing across the stack; OpenSSL bindings here also pull in older `libcrypt` weaknesses. | A deployment that never parses X.400 cert extensions sees lower realized impact; `high` chosen because the library is universally loaded by the platform. |
| **`addons/iot_drivers/tools/upgrade.py:204` → `medium` (not `high`).** | `high` (shell=True with formatted command). | The `commands` variable is constructed internally from an apt-packages file local to the IoT Box; reaching the sink from outside requires already having privileged access to the IoT box environment, which is a meaningful precondition. | If a future change feeds user input into `commands`, this should be re-elevated to `high`; the entry is also a lint-level signal to keep the construction trusted. |
| **`odoo/service/server.py:1479` → `low` (not `medium`).** | `medium` (any `shell=True` with `.format()` interpolation). | The interpolated value `nt_service_name` is internal config read at process startup; the pattern is *bad shape* but not currently exploitable. | If a future change reads `nt_service_name` from a less-trusted source (CLI arg, env var passed from a non-admin), the severity should be re-elevated. |
| **`addons/pos_qfpay/controllers/main.py:38` MD5 signature → `low`.** | `medium` (any MD5 in a security-bearing role). | The MD5 use is for QFpay notification-signature verification, gated by `consteq` constant-time comparison and the QFpay third-party API contract — practical collision attacks would require the attacker to choose both pre-images, which the QFpay payload contract makes difficult. | If QFpay's contract ever allows attacker-controlled payload prefixes, this should be re-elevated; the entry stands as a "weak hash in security role" flag. |

## §4. Deliberate exclusions (candidate findings dropped)

| Decision | Alternatives Considered | Why This Choice | Risks |
| --- | --- | --- | --- |
| **`odoo/http.py:1905` HMAC-SHA1 for CSRF tokens NOT flagged.** | Flag as CWE-327 (use of a broken / risky hash in HMAC construction). | NIST SP 800-131A Rev. 2 still classifies HMAC-SHA-1 as acceptable for authentication (as opposed to digital-signature use); AAP §0.3.2 explicitly lists the `database.secret` HMAC token machinery as an existing control. | Flagging this would be a false positive against a documented control; a future audit should revisit if NIST updates its guidance to deprecate HMAC-SHA-1 outright. |
| **`odoo/addons/base/models/res_users.py:1228-1231` rate-limiting NOT flagged.** | Flag as CWE-307 (Improper Restriction of Excessive Authentication Attempts). | The per-worker counter is a documented limitation, not a vulnerability (AAP §0.6.7); the project explicitly notes the limitation in `res_users.py:1228-1231`. | Misclassifying a documented limitation as a finding would contaminate the baseline and overstate the audit's signal. |
| **`addons/**/cr.execute("...%s" % self._table)` NOT flagged as CWE-89.** | Flag every f-string / `%`-format into `cr.execute` as SQL injection. | `_table` is an internal Odoo model attribute set at class-load time, never derived from user input; the `%s` substitution is into a hard-coded identifier and the parameterized values still use `cr.execute(query, params)`. | A custom addon that overrides `_table` from user input would change the analysis — out of scope for this audit and out of scope for Configs B/C/D's default rules. |
| **`safe_eval()` call sites NOT flagged.** | Flag every `safe_eval(...)` as CWE-94 (Code Injection). | `safe_eval` is the bytecode-filtered evaluator at `odoo/tools/safe_eval.py`; AAP §0.3.2 lists it explicitly in the do-not-falsely-flag list. | A scanner without context will flag these; the difference between Configs A and B/C/D on these sites is the expected delta and is recorded here. |
| **`file_open()` call sites NOT flagged as CWE-22.** | Flag any open-by-string-path as path traversal. | `file_open` delegates to `file_path()` which validates against the configured `addons_path` — paths cannot escape the addons sandbox. | Flagging would be a false positive against an existing control. |
| **`html_sanitize()` use NOT flagged as XSS.** | Flag every template rendering output that has been routed through `html_sanitize()`. | `html_sanitize()` (`odoo/tools/mail.py`) is the existing XSS-prevention control listed in AAP §0.3.2 and is the correct place for the project to neutralize untrusted HTML. | False-positive risk only; Configs B/C/D will likely flag these without context, generating noise we are deliberately omitting. |
| **`addons/web_unsplash/controllers/main.py:88` `requests.get(url)` NOT flagged as SSRF.** | Flag as CWE-918 (Server-Side Request Forgery). | The URL is bounded by an allowlist check `url.startswith(('https://images.unsplash.com/', 'https://plus.unsplash.com/'))` immediately above the request call; the host set is closed and trusted. | Allowlist enforcement makes this safe; flagging would be a false positive. If the allowlist is ever broadened or removed, re-evaluate. |
| **`addons/html_editor/controllers/main.py:601` `etree.fromstring(svg)` NOT flagged as XXE.** | Flag as CWE-611 (Improper Restriction of XML External Entity Reference). | The SVG content is fetched from a media-library endpoint configured by admin (`html_editor.media_library_endpoint`), not directly user-supplied; the case is borderline and was kept off the list per AAP §0.9.3 "honest under-reporting beats noisy over-reporting". | A future change that accepts user-uploaded SVG without the media-library hop would change the analysis — revisit then. This is one of three deliberate under-reports. |
| **`addons/account/models/account_move.py` SHA-256 hash-chain NOT flagged.** | Flag the inalterability hash chain as weak cryptography. | The hash chain *is* the control, not the vulnerability; AAP §0.3.2 lists "financial data + inalterability" as a project strength backed by SHA-256 chaining and the lock-date mechanism. | Flagging would invert the meaning of the control and confuse readers. |
| **`addons/mail/controllers/mail.py:220` `/mail/unfollow` with `csrf=False` NOT flagged.** | Flag as CWE-352 (Cross-Site Request Forgery). | The endpoint is intentionally CSRF-disabled because it is invoked from email clients (no session is present); the URL-embedded token IS the authentication artifact for the route. The inline comment at line 219 explains this design. | A reader who reads the route header in isolation will think CSRF is missing; the comment exists in source to prevent this misreading. |
| **All payment-webhook controllers with `csrf=False` NOT flagged** (Stripe, Adyen, PayPal, Paymob, Buckaroo, …). | Flag every CSRF-disabled POST endpoint. | External Payment Service Providers cannot present a CSRF token; webhooks are authenticated against a per-PSP cryptographic signature on the request body, not against a session-bound CSRF token. | A scanner without context will flag every payment webhook; Config A is honest about the legitimate exception class. |

## §5. Deviations from a literal reading of the directives

| Decision | Alternatives Considered | Why This Choice | Risks |
| --- | --- | --- | --- |
| **Trailing newline appended to `findings-config-a.json`.** | Write the literal JSON content with no terminator byte at all (a literal reading of AAP §0.6.1 "no trailing newline"). | The user-stated pass-criterion (Directive 2 verbatim) is `cat findings-config-a.json \| wc -l` returning `1`. POSIX `wc -l` counts newline bytes; a file with content but no `\n` returns `0`, which would FAIL the pass-criterion. A single trailing `\n` satisfies the pass-criterion AND keeps the JSON content on a single line with no embedded newlines. | A reader interpreting "no trailing newline" literally will see one byte of difference; the pass-criterion command demonstrates correctness on its own terms. |
| **Zero `critical`-severity findings reported.** | Re-classify the `addons/web/controllers/database.py` DB-manager auto-reset cluster (5 findings) as `critical`. | The severity rubric (AAP §0.6.4) reserves `critical` for *remote, unauthenticated code execution* or *authentication bypass on a public route with no preconditions*. The DB-manager cluster requires `admin_passwd == 'admin'` to be exploitable — that is one precondition, which puts the cluster at `high` per the rubric. | A reader who scores by worst-case outcome will defensibly say `critical`; the rubric is the deliberate tie-breaker recorded here. |
| **34 findings reported, not 0 (the empty-array fallback path is unused).** | Emit literal `[]` per the AAP §0.6.7 zero-findings edge case. | The audit did find vulnerabilities; the empty-array path is reserved for the case where no defensible finding exists. AAP §0.9.3 "honest under-reporting beats noisy over-reporting" means "drop unsure findings", not "report zero unconditionally". | A reader expecting a tightly curated single-page summary may find 34 findings verbose; the executive deck condenses these into KPI cards and CWE-family groupings. |

## §6. Existing controls acknowledged (false-positive avoidance)

Each row is the explicit antidote to the "Configs B/C/D will flag these naively" risk and prevents accidental re-introduction of false positives during merge / reconciliation.

| Decision | Alternatives Considered | Why This Choice | Risks |
| --- | --- | --- | --- |

| **`safe_eval()` at `odoo/tools/safe_eval.py` — relied upon.** | Flag every callsite of `safe_eval(...)` as CWE-94 (Code Injection). | `safe_eval` is the bytecode-filtered evaluator that strips dangerous opcodes; AAP §0.3.2 lists it as an existing control. | None; scanners without context will flag these and produce the expected Config A vs B/C/D delta. |
