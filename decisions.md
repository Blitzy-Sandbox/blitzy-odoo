# Decision Log — Blitzy-Odoo SonarQube Scan (Config I)

This decision log realizes the Explainability rule of the Agent Action Plan (AAP §0.7.2): every non-trivial implementation choice made during the one-shot static security analysis of `blitzy-odoo` using SonarQube Community Build is recorded here, with rationale, alternatives, and risks. The task it documents is a single ephemeral scan producing the normalized artifact `findings-config-i.json` at the repository root; no source-tree file is modified. The repository scope is the `blitzy-odoo` working copy, a strategic fork of Odoo 19.0, branch `config-i` at head commit `b58d620c4fb`. Every row in the table below reflects a choice that a competent engineer could have reasonably made differently; the cell prose names the alternative paths, the choice made, and the residual risks each choice carries. The rows enumerated below are the minimum mandatory set required by the AAP; additional non-trivial decisions discovered during execution are to be appended to the table rather than embedded as rationale in code comments. This file is the single source of truth for "why" decisions related to this scan; sibling deliverables (`findings-config-i.json` and `presentation.html`) hold the data and executive-facing narrative respectively.

| --- | --- | --- | --- | --- |
| **1** | SonarQube image tag: rolling `community` (i.e., `docker pull sonarqube:community`) | Pin to a specific numeric Community Build tag (e.g., `sonarqube:25.x.x-community`); use the LTA image; build a custom image with rules pre-installed | The user's Directive 1 names the artifact verbatim as `sonarqube:community`; using the rolling tag yields the latest rule set and CWE coverage at scan time, and pinning would deviate from the literal prompt. The scan is ephemeral, stateless, and single-run, so rule-set drift between runs is acceptable. | Rule-set changes between runs can shift the finding count or CWE encoding; mitigated by recording the resolved image digest at run time and including it in the operational log alongside the scan. Cross-tool comparison runs executed on the same day against the same image digest are unaffected. |
| **2** | Database: embedded **H2** (the `sonarqube:community` image default) | External PostgreSQL via `SONAR_JDBC_URL` (production-grade, persistent); ephemeral PostgreSQL sidecar via `docker compose`; SQLite tunneling | The scan is ephemeral and single-run; H2 is the image default and requires no extra provisioning; data persistence across runs is explicitly NOT required because the container is destroyed at teardown. Avoiding an external database keeps the workflow to a single `docker run` invocation. | H2 is unsupported for production use by SonarSource and is not recommended for instances that need to retain history; this is not an issue here because the project and its database are destroyed at teardown, so durability and concurrent-access guarantees are irrelevant to this task. |
| **3** | First-login `admin/admin` handling: tolerate-and-bootstrap | (a) Pre-set the admin password via `POST /api/users/change_password`; (b) generate a user token via `POST /api/user_tokens/generate` and pass `-Dsonar.token=<token>`; (c) attempt the scan blindly and let the CLI fail with 401 retries | The implementation first calls `change_password?login=admin&previousPassword=admin&password=admin` (idempotent on a fresh container; 400 is ignored if the password has already been changed) and then proceeds with `-Dsonar.login=admin -Dsonar.password=admin` per the user's Directive 3 invocation. If 401 persists, fall back to generating a token via `/api/user_tokens/generate?name=blitzy-scan` and re-invoke the scanner with `-Dsonar.token=...`. This honors the user's literal command while remaining robust against newer SonarQube CE versions that mandate password change before any API call. | If a future SonarQube version blocks default credentials entirely (no bootstrap endpoint either), the change-password call may fail; the token-generation fallback is the durable path. Token storage is not persisted because the container is destroyed at teardown, so leakage risk is bounded to the in-process scan flow. |
| **4** | Severity fold mapping: `BLOCKER`+`CRITICAL` → `critical`, `MAJOR` → `high`, `MINOR` → `medium`, `INFO` → `low` | Map only `BLOCKER → critical` and `CRITICAL → high` (one-to-one with severity intensity); use the SARIF severity model (`error`/`warning`/`note`); preserve Sonar severity verbatim with no fold | Implement the user's field-mapping table verbatim — both `BLOCKER` and `CRITICAL` fold to `critical`, `MAJOR` folds to `high`, `MINOR` folds to `medium`, `INFO` folds to `low`. Encoded as a deterministic, total function over the Sonar severity enum so re-runs are byte-identical; an unknown severity raises an explicit error rather than silently dropping the field. | Folding `BLOCKER` and `CRITICAL` together loses a distinction that some Sonar consumers rely on; downstream comparators must therefore avoid using `critical` as a single-bucket proxy for SonarQube's `BLOCKER` rank specifically. The trade-off is documented here so the cross-tool comparator can normalize accordingly. |
| **5** | CWE extraction order: tags → rule-description regex → sentinel `"CWE-UNMAPPED"` | (a) Use only `tags`, leave the field `null` when absent; (b) call an external CWE-mapping service or local CWE database; (c) infer from the rule key naming convention only | Order: (1) match each item in `issue.tags` against `^cwe-(\d+)$` (case-insensitive) and emit `CWE-<n>` for the first match; (2) if no tag matches, fetch `/api/rules/show?key=<ruleKey>` and regex-scan `htmlDesc`/`mdDesc` for the first `CWE-?\d+` occurrence; (3) if no inference is possible, emit the documented sentinel `"CWE-UNMAPPED"`. This honors the user's "infer from rule description" clause in the field-mapping table while keeping the pipeline deterministic. | The `/api/rules/show` fallback adds extra HTTP requests; mitigated by caching the rule→CWE map within the run so each rule key is fetched at most once. Regex inference may select the wrong CWE when a rule description references multiple CWEs; the first match wins by design (deterministic). The `"CWE-UNMAPPED"` sentinel is documented here so downstream comparators recognize and group such entries. |
| **6** | UTF-8-safe description truncation at 200 characters | Truncate by raw bytes (`message.encode('utf-8')[:200]`, which can split multi-byte sequences); truncate to 197 characters and append a literal `"..."` ellipsis; truncate by code points then trim back to the nearest word boundary | Python `str` indexes by Unicode code point, so `message[:200]` is inherently safe on character boundaries and never produces invalid UTF-8. No ellipsis is appended because the user's schema example shows raw truncation. The 200 cap is measured in code points to match the user's "characters" wording in the field-mapping table. | Some context may be lost at the truncation boundary; the full message remains retrievable from SonarQube's `/api/issues/search` response if needed (out of scope for this artifact). Grapheme clusters composed of multiple code points (e.g., combining marks) may be split because Python operates on code points rather than grapheme clusters; this is an acceptable trade-off given the absence of combining-mark-heavy content in Sonar rule messages. |
| **7** | Path normalization for the `file` field: strip the `<projectKey>:` prefix from the Sonar `component` string | Keep the full `<projectKey>:<relative path>` Sonar `component` string verbatim; emit only the file basename; emit the absolute on-disk path from the container | Sonar returns `component` shaped `blitzy-odoo:<relative path>`; the user's schema example shows `<relative path>` only. Stripping the project-key prefix yields a clean repo-relative path that matches what other security tools in the cross-tool comparison emit, enabling apples-to-apples diffing on file identity. | If the project key changes in a future configuration, this stripping rule must be updated; mitigated by deriving the prefix from the runtime `sonar.projectKey` value rather than hard-coding `"blitzy-odoo:"`. Sonar may emit directory-level component entries without a usable line number; those are filtered out of the issue stream because the schema requires a populated `line` field. |
| **8** | Empty-result encoding: write the two-byte literal `[]` with no trailing newline | Write the four-byte object `null`; write the wrapper `{"findings": []}`; omit the file entirely; emit `[]\n` (with trailing newline) | The user's Directive 5 states verbatim: "If zero findings, write `[]`." Writing exactly the two bytes `0x5B 0x5D` satisfies the `wc -l` verification gate, which returns `1` only when the file has content but no terminating `\n`. | Some downstream parsers and editors may complain about (or auto-correct) the missing trailing newline; this is explicitly required by the verification gate, so consumers must be configured not to re-write the file with a trailing newline. The constraint is documented here so the behavior is not mistaken for a bug. |
| **9** | Pagination strategy: `ps=500` (API maximum) with sequential `p=<n>` increments until the total is exhausted | Use the API default `ps=100` (more requests, same payload total); attempt a single `ps=10000` mega-page (not supported by the API); recursively split the query by component key prefix | Iterate `p=1`, `p=2`, … with `ps=500` until `(p × ps) ≥ paging.total`; stop after the page that fully covers the reported total. SonarQube returns at most 10,000 results across all pages under a single query, which is well above the expected issue count for `blitzy-odoo`. | If the issue count exceeds the 10,000 hard cap, results beyond that ceiling are silently dropped by SonarQube; if observed, the implementation will narrow the query by component-key sub-path and record an additional decision row here. The page size of 500 minimizes request count while staying within the documented API maximum. |
| **10** | Quality-gate behavior: pass `-Dsonar.qualitygate.wait=true` to the scanner | Skip the wait flag and exit immediately after the analysis upload (scanner returns before the compute engine finishes); poll `/api/qualitygates/project_status` manually after the scanner exits | The user's Directive 3 example invocation includes `-Dsonar.qualitygate.wait=true`; the CLI blocks until the compute engine finishes, which makes the wall-clock scan duration meaningful and ensures the quality-gate result is available before issue export begins. | Adds compute-engine wait time to the run; offset by capturing a precise end-to-end duration that is impossible to obtain from CLI exit alone, and by avoiding race conditions where `/api/issues/search` is called before analysis ingestion completes. |
| **11** | Container teardown placement: shell `trap` / Python `try/finally` to guarantee execution on success and failure | Run teardown only on the success path; rely on `docker run --rm` to auto-remove the container on exit; rely on the OS to reap the container when the host shell exits | Wrap the entire scan flow in a teardown block that runs on success AND failure (`trap 'docker stop sonarqube-test 2>/dev/null; docker rm sonarqube-test 2>/dev/null' EXIT` or Python `try/finally`). Honors the "ephemeral" requirement of the AAP and frees port 9000 regardless of scan outcome. `docker run --rm` is incompatible with `-d` semantics in this image, so the explicit teardown is required. | If the teardown itself fails (e.g., Docker daemon crashed mid-run), port 9000 may remain bound to the orphaned container; mitigated by a `docker rm -f sonarqube-test` fallback that force-removes the container without waiting for graceful shutdown. |
| **12** | Rationale lives in this decision log only — never in code comments | Sprinkle short "why" comments at the line of each non-trivial decision in shell or Python scripts; duplicate rationale in both places for convenience | Per the Explainability rule, the "why" for every non-trivial choice lives ONLY in `decisions.md`; any source script produced during execution documents only **what** it does, not **why** it does it. | **13** | Toolchain install path on Ubuntu 25.10 host: SonarSource zip distribution of `sonar-scanner` CLI `8.1.0.6389` (installed at `/opt/sonar-scanner-8.1.0.6389-linux-x64`, symlinked into PATH via `/usr/local/bin/sonar-scanner`, bundled OpenJDK 21.0.9 Temurin JRE) vs. the literal `apt install sonar-scanner` command in Directive 1 | (a) Force `apt install sonar-scanner` to run, observe its failure on Ubuntu 25.10 where the package is unavailable, and abort the task without producing any artifact; (b) backport an apt `sonar-scanner` package to Ubuntu 25.10 via a third-party PPA or by rebuilding the Ubuntu 24.04 source package against 25.10; (c) install the official SonarSource zip distribution of the same CLI version (which bundles its own OpenJDK 21.0.9 Temurin JRE, so no host Java is needed) | The actual execution host is Ubuntu 25.10, not the Ubuntu 24.04 LTS originally assumed by AAP §0.4.1; the `sonar-scanner` apt package is not published for 25.10, so the literal Directive 1 command would fail at install time. The SonarSource zip distribution ships the exact same `sonar-scanner` CLI binary, so `sonar-scanner --version` still returns a version string and Directive 1's pass criterion is met verbatim. The deviation is from the literal `apt install sonar-scanner` command form, not from Directive 1's pass/fail condition; the scan flow, the scanner arguments in Directive 3, and the produced artifact are unaffected by the install path. The Explainability rule (AAP §0.7.2) requires every deviation from the literal interpretation to have an explicit entry in the decision log; this row realizes that requirement. | A manual upgrade path is required for future scanner version bumps because the package manager no longer owns the binary; mitigated by pinning the install location at `/opt/sonar-scanner-<version>` so the symlink target at `/usr/local/bin/sonar-scanner` can be re-pointed by re-running the install script on host upgrade. The bundled OpenJDK 21.0.9 Temurin JRE inside the zip means a CVE against OpenJDK 21 requires a fresh scanner-zip refresh rather than a host JRE patch — acceptable for an ephemeral, single-run scan; cross-referenced from the External Documentation entry on the `sonar-scanner` apt package in the References section below so the deviation is reachable from both the table and the reference list. |
| **14** | Mermaid rendering lifecycle in `presentation.html`: (a) on script load, cache the original Mermaid source of every `<pre class="mermaid">` into a `data-mermaid-source` attribute, then on each `Reveal` `ready` / `slidechanged` event reset `textContent` and remove `data-processed` before calling `mermaid.run({ nodes })` for the current slide; (b) await `document.fonts.ready` before any `mermaid.run()` invocation, falling back to `Promise.resolve()` when `document.fonts` is unsupported | (a) Call `mermaid.run()` exactly once during `Reveal.on('ready', ...)` with no per-slide re-render — simplest code path; (b) call `mermaid.run()` on every `slidechanged` without preserving the original source, accepting that Mermaid skips already-processed elements; (c) call `mermaid.run()` immediately on `ready` with no `document.fonts.ready` gate; (d) use a `MutationObserver` instead of `data-mermaid-source` caching to trigger re-render | reveal.js hides off-screen slides with `display:none`, so a single render on `ready` produces 0×0 SVGs for any slide that is not currently visible — once Mermaid sets `data-processed`, those elements cannot be retargeted by a later `mermaid.run()`. Caching the raw source in `data-mermaid-source` lets each slide-entry handler reset `textContent` and clear `data-processed`, so `mermaid.run()` produces a correctly sized SVG every time the slide becomes visible. Separately, Mermaid measures text widths from the DOM at render time; when the Inter webfont has not yet downloaded, measurements are taken against the fallback (typically narrower) font, and rendered labels then overflow once the real font swaps in — awaiting `document.fonts.ready` before any `mermaid.run()` removes the measurement-versus-paint race and yields stable, non-clipped diagrams. This row is the single source of truth for these decisions per the Explainability rule (AAP §0.7.2); the corresponding script lines in `presentation.html` carry only brief WHAT-style comments that reference this row. | The cache mechanism adds a one-time DOM pass at script load to hydrate each `<pre class="mermaid">` element; the per-slide reset adds one DOM read and two attribute mutations per slide entry — both negligible. If `document.fonts` is unsupported (very old browsers without the CSS Font Loading API), the code falls back to an immediately resolved `Promise.resolve()` so rendering still runs but may exhibit the original measurement-versus-paint clip in those environments; mitigated by the fact that the deck targets modern browsers (every browser shipping a reveal.js 5.1.0–compatible runtime already supports `document.fonts`). If a future Mermaid release removes the `data-processed` marker semantics or changes how `mermaid.run({ nodes })` handles already-rendered elements, the reset-and-rerun logic in `renderMermaidOnSlide` would need to be revisited; the AAP pins Mermaid at `11.4.0` so this risk is bounded to a deliberate version bump. |

## Traceability Matrix — Non-Applicability

The Explainability rule requires a bidirectional traceability matrix for migrations and refactors, mapping every source construct to its target implementation with one-hundred-percent coverage. This task is a static security scan, not a migration or refactor — no source construct is moved, renamed, refactored, or replaced, and no existing file in the working tree is modified. The deliverables (`findings-config-i.json`, `decisions.md`, `presentation.html`) are net-new artifacts at the repository root; the `blitzy-odoo` codebase is REFERENCE-only input to SonarQube. Accordingly, no traceability matrix is produced for this task. This gap is acknowledged here explicitly per the rule's "Unexplained deviations are treated as defects" clause, so its absence is a documented design decision rather than a silent omission.
