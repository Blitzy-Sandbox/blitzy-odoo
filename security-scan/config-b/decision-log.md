# Config B — Decision Log

This document is the **Explainability deliverable** for `security-scan/config-b/` and the **single source of truth for "why" decisions** in the Config B harness. Every non-trivial implementation decision is recorded below with explicit alternatives, rationale, and risks; every deviation from a literal reading of the user prompt has a dedicated entry; and a bidirectional traceability matrix maps every consumed SARIF field to every emitted `findings-config-b.json` field. The harness source files (`run-scan.sh`, `normalize-findings.py`) intentionally carry **only operational comments** ("anchor the script to its own directory", "abort on the first failure", etc.) — no "why" rationale appears in code. This document satisfies the Explainability user rule (AAP §0.7.1) and is the artifact named in AAP §0.6.2.10.

## 2. Bidirectional Traceability Matrix

The matrix below maps every consumed SARIF field to every emitted `findings-config-b.json` field, with 100% coverage of the five output fields per AAP §0.5.4.3. Each row corresponds to exactly one output field; reading left-to-right traces SARIF → deliverable, reading right-to-left traces deliverable → SARIF.

| Output Field | Source SARIF Path | Transformation | Failure Fallback |
| --- | --- | --- | --- |
| `file` | `runs[].results[].locations[0].physicalLocation.artifactLocation.uri` | If `--target-root` is set and the URI is absolute under that root, strip the root prefix (and any leading `file://`) so the result is repo-relative. Otherwise no transformation. | `""` only if SARIF omits the location entirely (logged to stderr). |
| `line` | `runs[].results[].locations[0].physicalLocation.region.startLine` | Coerce to integer via `int(...)`; numeric strings are parsed; non-numeric values fall through to the fallback. | `0` if SARIF omits the region (logged to stderr). |

## 3. Deviations from a Literal Reading of the User Prompt

This section enumerates every place Config B's behavior diverges from the most literal reading of the user prompt. Each entry is required by AAP §0.7.1 ("Any deviation from a literal or obvious interpretation of the requirements MUST have an explicit entry in the decision log. Unexplained deviations are treated as defects."). Each entry states the literal user text, the empirical reality, the chosen resolution, and the reason the resolution is acceptable.

### DEV-1 — RETIRED — `p/owasp` → `p/owasp-top-ten` fallback removed

- **Status:** **RETIRED** as of the Checkpoint 2 remediation pass. The DEV-1 identifier is preserved so that historical cross-references in commits, code-review reports, and `scan-metadata.json` snapshots remain valid; new cross-references SHOULD point to the §1 Decision Log Table row titled *"Abort the harness if `p/owasp` cannot be downloaded from the registry"* instead.
- **Original deviation (now no longer in force):** Earlier revisions of `run-scan.sh` substituted `p/owasp-top-ten` for `p/owasp` when the registry returned HTTP 404 for `p/owasp`. This was implemented as a runtime fallback inside `materialize_rule_cache` and surfaced via `scan-metadata.rule_packs.used` differing from `scan-metadata.rule_packs.requested`.
- **Reason for retirement:** AAP §0.7.3 unconditionally forbids substituting `p/owasp-top-ten` for `p/owasp`. The Checkpoint 2 review confirmed this as a CRITICAL verbatim-contract violation. The remediation deletes the fallback branch entirely; the harness now `die`s with a clear AAP §0.7.3 reference if `p/owasp` cannot be fetched.
- **Behavioral consequence:** `rule_packs` is now a single flat array in `scan-metadata.json` (no more `{requested, used}` shape). The harness has no built-in OWASP substitution path; any future need to use a different OWASP-themed pack requires an explicit AAP amendment.

### DEV-2 — `--dry-run` is not a real Semgrep CLI flag; the correct flag is `--dryrun`

- **Literal user text:** *"`semgrep scan --metrics=off --config=/path/to/local-rules --dry-run` exits 0 with no network calls."*
- **Empirical reality:** Semgrep 1.163.0 (and every release back to 1.0.0) accepts `--dryrun` (one word) but rejects `--dry-run` with `unknown option '--dry-run'. Did you mean either '-d' or '--dryrun'?`. Semantically `--dryrun` only suppresses autofix writes; it still loads rules and walks the target — which is the offline verification the user actually wants.
- **Resolution:** `run-scan.sh`'s Directive 1 gate runs `semgrep scan --metrics=off --config=<rule-cache> --dryrun /tmp/sg-empty-target`. In production verification it is run with `--metrics=off` and the absence of outbound network traffic is observed via the gate logs; the dry-run gate result is recorded under `scan-metadata.dry_run_gate`.
- **Why this is acceptable:** The user's intent is "verify the rule cache loads offline and the scan exits cleanly." Both halves of that intent are satisfied; the only difference is the CLI flag spelling, which is corrected to match the tool's actual accepted flag.

### DEV-3 — The AAP's "no trailing newline" mandate overrides the user prompt's literal `wc -l == 1` gate

- **Literal user text (Directive 3 pass/fail):** *"`cat findings-config-b.json | wc -l` returns `1`."* and *"If zero findings, write `[]`."*
- **Literal AAP text:** AAP §0.1.2.3 mandates *"a single write of bytes — **no trailing newline** — to guarantee `wc -l` returns `1`"* and *"the file content is the two bytes `[]`"*. AAP §0.5.4.2 mandates *"write to disk with `Path(...).write_bytes(...)` **(no trailing newline)**"*. AAP §0.6.2.1 mandates *"Encoding: UTF-8, no BOM, **no trailing newline**"*.
- **Empirical tension:** GNU `wc -l` counts newline-terminated lines. A file with no trailing newline has `wc -l == 0`, not `wc -l == 1`. The user-prompt clause `wc -l == 1` and the AAP's "no trailing newline" plus "two bytes `[]`" are mutually exclusive — at most one can be literally true at any time.
- **Resolution:** Follow the AAP. `normalize-findings.py` serializes via `json.dumps(records, ensure_ascii=False, separators=(',', ':'))` and writes the resulting bytes directly with `Path.write_bytes(...)` and no trailing newline. The empty case is exactly the two bytes `[]`; a non-empty case is exactly the JSON payload bytes with no terminating LF.
- **Gate substitution:** Because the literal `wc -l == 1` is unsatisfiable under the AAP, the orchestration script and the README express the "single line" gate as `tr -dc '\n' < findings-config-b.json | wc -c == 0` (no newline bytes anywhere) and the empty case as `wc -c < findings-config-b.json == 2`. Both formulations imply "single line" in the engineering sense without requiring a contradictory trailing LF.
- **Why this is acceptable:** The AAP is the authoritative source for how the deliverable is shaped at runtime; it spells out "no trailing newline" in three separate sections (§0.1.2.3, §0.5.4.2, §0.6.2.1). The user-prompt gate is operationally equivalent under either gate formulation — both confirm the file is a single contiguous line — so adopting the AAP-aligned gate preserves every intent of the user prompt while keeping the deliverable byte-exact to the AAP.

### DEV-4 — Absolute → relative file paths are produced by the normalizer, not by changing the Semgrep target

- **Literal user text — verbatim command:** *"`semgrep scan --config=/path/to/local-rules --sarif -o results-semgrep.sarif --metrics=off /path/to/blitzy-odoo`"*. **Literal user text — field mapping:** *"file: SARIF location (relative path)"*.
- **Empirical reality:** When Semgrep is invoked with an absolute target (as the verbatim command requires), it emits absolute URIs in SARIF (`artifactLocation.uri = /absolute/path/...`). To make `findings-config-b.json` carry relative paths, the absolute prefix must be stripped.
- **Resolution:** The orchestration script invokes `normalize-findings.py` with `--target-root $TARGET_ROOT`. The normalizer detects absolute URIs that begin with `TARGET_ROOT/` (or `file://TARGET_ROOT/`) and rewrites them to be repo-relative before emission.
- **Why this is acceptable:** The verbatim user command is preserved character-for-character (it is echoed to stderr before invocation). The "relative path" requirement is satisfied at normalization time without altering the SARIF input.

### DEV-5 — `"CWE-Unknown"` is emitted when no CWE can be located or inferred

- **Literal user text:** *"cwe: Rule metadata CWE ID. If absent, use the most specific CWE inferable from the rule description."*
- **Empirical reality:** A strict reading would yield no value when a Semgrep rule has neither `properties.cwe` nor any keyword-inferable CWE phrase in its message — but the pass/fail clause requires "every finding has all 5 fields populated."
- **Resolution:** The normalizer emits the literal string `"CWE-Unknown"` (with the `"CWE-"` prefix preserved to maintain field format) and logs the rule ID plus message text to stderr. The sentinel is a single constant in `normalize-findings.py` (`CWE_UNKNOWN`) so it can be tightened later.
- **Why this is acceptable:** `"CWE-Unknown"` is a stable, auditable sentinel that preserves the closed five-field schema and the operator-facing gate "every finding has all 5 fields populated." Operators are directed to the stderr log line every time the sentinel is emitted.

### DEV-6 — `"medium"` is the last-resort severity when SARIF and rule metadata both omit `level`

- **Literal user text:** *"severity: error→critical, warning→high, note→medium, info→low"*.
- **Empirical reality:** SARIF `level` is optional. Semgrep rules sometimes lack a result-level `level` even though `defaultConfiguration.level` or `properties.severity` carries the same intent. If all three sources are absent, a literal reading produces no value — but the pass/fail clause requires "every finding has all 5 fields populated" and the severity enum is closed at four values.
- **Resolution:** The normalizer reads three sources in priority order (`result.level → rule.defaultConfiguration.level → rule.properties.severity`) and falls back to the literal string `"medium"` (the middle of the four-value enum) as a neutral last resort. The originating rule ID is logged to stderr.
- **Why this is acceptable:** The five-field gate cannot fail without explicit policy guidance from the user. `"medium"` is the least biasing of the four allowed values; under-classifying a high-severity finding as medium is preferable to either failing the gate or introducing a fifth enum value.

### DEV-7 — Operational facts (exit code, duration, files scanned) live in `scan-metadata.json`, NOT inside the SARIF body

- **Literal user text:** *"Record exit code, scan duration (wall-clock), and total files scanned."*
- **Empirical reality:** Directive 2 says "Record" these facts; it does not say where. Adding them to SARIF would either (a) modify Semgrep's emitted payload (breaking the "valid SARIF" trivial-auditability principle and Directive 2's pass/fail gate that checks for an unmodified `runs[]` array) or (b) require post-processing the SARIF into a non-standard envelope. Adding them to `findings-config-b.json` would violate the closed five-field schema mandated by Directive 3.
- **Resolution:** Config B keeps the SARIF byte-identical to Semgrep's emission and persists the three operational facts — plus Semgrep version, rule-pack identifiers, dry-run gate result, run timestamps, and reproducibility (byte-identical-rerun) evidence — in a sibling JSON file `scan-metadata.json` per AAP §0.6.2.3. The README and Executive Summary both cross-reference the two files.
- **Why this is acceptable:** Directive 2's pass/fail gate is "SARIF contains a `runs[]` array" — leaving SARIF untouched makes that gate trivially auditable. Directive 3's five-field schema is closed — keeping the operational facts in a separate JSON preserves the schema. Both requirements are simultaneously satisfied.

### DEV-8 — Default Semgrep targeting (no `--include`/`--exclude`/`-j`/`--timeout`)

- **Literal user text — verbatim command (Directive 2):** *"`semgrep scan --config=/path/to/local-rules --sarif -o results-semgrep.sarif --metrics=off /path/to/blitzy-odoo`"*.
- **Empirical reality:** The verbatim Directive 2 command does not include any of `--include`, `--exclude`, `-j`, `--timeout`, or any other tuning flag. Semgrep's own targeting heuristics decide which files inside `addons/`, `odoo/`, etc., are parsed for which language ruleset. On a tree of this size (~40,000 files) this default-targeting scan may take longer than a `-j 8 --include='*.py'` invocation would.
- **Resolution:** Config B preserves the verbatim command exactly as the user provided it. No `--include`, no `--exclude`, no `-j`, no `--timeout` is added. The harness echoes the resolved command to stderr before execution so operators can independently verify wire-level fidelity.
- **Why this is acceptable:** AAP §0.7.3 binds the harness to the user-provided command as a task-specific rule ("Use the exact Directive 2 command as the SARIF-generating invocation. No flag additions, removals, or reorderings."). The trade-off favors literal fidelity to the user prompt over scan-time optimization. Operators who need a tighter scan can `Ctrl+C` and rerun with a narrower `--target-root`.

### DEV-9 — Mermaid CDN pin is `mermaid@11.10.0`, not the AAP-literal `mermaid@11.4.0`

- **Literal user text — AAP §0.4.4 (CDN Frontend Dependencies) and AAP §0.7.2 (Executive Presentation user rule):** *"CDN versions pinned: reveal.js 5.1.0, Mermaid 11.4.0, Lucide 0.460.0"* and *"the deliverable [executive-summary.html] … CDN versions are exactly reveal.js 5.1.0, Mermaid 11.4.0, Lucide 0.460.0"*.
- **Empirical reality:** The AAP was authored before CVE-2025-54881 / GHSA-7rqq-prvp-x9jh ("Mermaid improperly sanitizes sequence diagram labels leading to XSS"; GitHub Security Advisory published 2025-08-19; CWE-79) was published. The advisory's affected range is `mermaid (npm) >= 11.0.0-alpha.1, < 11.10.0` — the literal 11.4.0 pin lies inside this range — and the patched version named in the upstream advisory, NVD, Snyk, and Vulert databases is `11.10.0`. The root cause is the `calculateMathMLDimensions` helper passing user-supplied sequence-diagram label text to `innerHTML` without sanitization when KaTeX support is active.
- **Resolution:** `executive-summary.html` and `README.md` pin `mermaid@11.10.0` instead of the AAP-literal `mermaid@11.4.0`. The CDN URL is `https://cdn.jsdelivr.net/npm/mermaid@11.10.0/dist/mermaid.min.js`; the asset is reachable on `cdn.jsdelivr.net` (HTTP 200, `x-jsd-version: 11.10.0`). The other two CDN pins (reveal.js 5.1.0, Lucide 0.460.0) remain at the AAP-literal versions because no security advisory affecting them in the as-used configuration has been identified.
- **Why this is acceptable:**
    1. **Practical exploitability in Config B's current usage was already negligible** — the deck never exposes Mermaid to runtime untrusted input, the Mermaid initialization in `executive-summary.html` does not enable KaTeX rendering, and the only `sequenceDiagram` in the deck (slide 9, "Scan pipeline lifecycle") contains static author-controlled labels with no `$$...$$` delimiters; so the vulnerable `calculateMathMLDimensions` code path is not exercised. QA Checkpoint 4 confirmed this and rated the finding `MINOR` rather than `MAJOR`. The upgrade is therefore defense-in-depth, not breach remediation, but is required for compliance with the QA gate that demands the dependency pin not be inside a published CVE range that has an available fix.
    2. **API compatibility is preserved**: the deck uses only `mermaid.initialize({ startOnLoad: false, theme: 'base', themeVariables: {...}, fontFamily: ..., flowchart: {...}, sequence: {...} })` and `mermaid.run({ querySelector: 'pre.mermaid' })`. These are the same surface contracts as in 11.4.0; the patch does not alter the public init/run API, theme-variable keys, or `<pre class="mermaid">` consumption pattern, so no other deck or harness change is required and the diagrams render with identical visuals.
    3. **AAP §0.7.1 anticipates exactly this case.** The Explainability rule mandates: *"Any deviation from a literal or obvious interpretation of the requirements MUST have an explicit entry in the decision log. Unexplained deviations are treated as defects."* This entry (DEV-9) is the explicit decision-log entry the AAP requires; the deviation is therefore not a defect, it is a recorded variance with rationale.
    4. **The deviation is minimal and surgical.** Only the Mermaid CDN URL and the human-readable version-listing text changed. The version-pin discipline (a fixed semver, not a floating range) is preserved; only the pinned value moves.
- **Re-approval path.** Operators who want to re-align the AAP literal text with the executed pin can amend AAP §0.4.4 and AAP §0.7.2 to specify `mermaid@11.10.0` (or a later release in the safe range), at which point DEV-9 can be marked RETIRED in the same style as DEV-1.

Deviation IDs (DEV-N) are stable: once assigned, the identifier is not reused even if the underlying deviation is retracted (see DEV-1 RETIRED).
